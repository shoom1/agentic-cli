# Agentic CLI - Shared Framework for Agentic Applications

## Project Overview

Agentic CLI is a shared library providing the core infrastructure for building domain-specific CLI applications powered by LLM agents.

## Tech Stack

- **Language**: Python 3.12+
- **CLI UI**: `thinking-prompt` 0.4 (`>=0.4,<0.5`) - enhanced CLI with thinking boxes, markdown and dialogs
- **Workflow**: Google ADK 2 (2.12+, the default) + Deep Agents (0.7.x, `deepagents` extra: LangChain's `create_agent` with selected Deep Agents middleware) - orchestration backends selectable via settings; LangGraph (`langgraph` extra) is deprecated, removed in 0.8.0
- **Models**: `agentic_cli.models` (provisional) - references, roles, the shipped table and the catalog, with no provider SDK (listers over `httpx`); two adapters build the SDK objects: ADK's own model classes (`Gemini`, `AnthropicLlm`, `OpenAIResponsesLlm`, plus our `OpenAICompatibleLlm`, on the `openai` SDK) and the LangChain partner packages (`langchain-google-genai`, `langchain-anthropic`, `langchain-openai`, `langchain-openrouter`; the `deepagents` and `langgraph` extras), which Deep Agents and LangGraph share
- **Config**: `pydantic-settings` - type-safe configuration
- **Logging**: `structlog` - structured logging

## Branching Strategy

- **main**: Stable branch, matches latest release. Only updated via merges from `develop` when releasing.
- **develop**: Integration branch for ongoing work. Small fixes can be committed directly here.
- **feature/\***: Feature branches for larger changes. Branch from `develop`, merge back to `develop`.
- **fix/\***: Fix branches for fixing issues. Branch from `develop`, merge back to `develop`.
- **refactor/\***: For larger refactoring changes. Branch from `develop`, merge back to `develop`.

Workflow:
1. For small fixes: commit directly to `develop`
2. For features: create `feature/<name>` (or `fix/<name>` or `refactor/<name>`) from `develop`, work there, merge back to `develop`
3. When ready to release: merge `develop` → `main` and tag the release

### What NOT to commit
- `docs/` is gitignored on purpose (see `.gitignore`). It is a scratchpad for review notes, plans, and internal analysis. **Never `git add docs/…` or suggest committing anything under `docs/`.** If a document belongs in the repo, it lives elsewhere (README, CHANGELOG, top-level `*.md`).

## Development Principles

### Code Style
- Follow PEP 8 style guidelines
- Use type hints throughout
- Prefer descriptive variable names

### Key Design Decisions
- **Abstract base classes**: BaseCLIApp and BaseWorkflowManager for domain extension
- **Pluggable orchestrator**: ADK (the default) and Deep Agents backends, selectable via settings (`settings.orchestrator`, routed by `workflow/factory.py::_BACKENDS`); LangGraph is deprecated and 0.8.0 removes it. Sessions do not move between backends: a conversation runs on one backend for its whole life (`settings.orchestrator` is the backend of new conversations; `/new <backend>` picks another; `/resume`, `--resume` and `--continue` open a conversation on the backend that keeps it, the run's services handed over; a model switch never changes it)
- **Lazy initialization**: Defer heavy imports until needed
- **Event-based streaming**: Real-time updates via AsyncGenerator
- **UI-agnostic workflow**: WorkflowEvent objects can be consumed by any UI

### Key Design Patterns
- **Tool error handling**: All tools return `{"success": bool, ...}` dicts. Never raise `ToolError`. An exception that still escapes a tool is a bug, but it costs one call rather than the turn: on ADK, `workflow/adk/tool_error_plugin.py::ToolErrorPlugin` turns it into an error dict; on Deep Agents, `workflow/deepagents/middleware.py::ToolCallErrorMiddleware`, inside the permission gate, gives the same result, `{"success": false, "error": "<tool> failed: <Type>: <message>"}` cut to 500 characters (both use `workflow/tool_errors.py`). A call to a tool name the agent does not have gets ADK's own text, its first two lines (`unknown_tool_result`: "nope failed: ValueError: Tool 'nope' not found." and the agent's tools by name), logged `tool_not_found` at info (the model's mistake): on ADK the permission gate lets ADK's stand-in through (`is_unknown_tool`: a bare `BaseTool` described "Tool not found", which runs nothing; contract-tested) and `ToolErrorPlugin` answers its lookup error; on Deep Agents the gate answers it. It catches `Exception`, never `BaseException`, so cancelling still cancels; an exception out of `task` (a sub-agent's model or run failing, its summary or overflow included: its own tools' errors are results already) is answered as ADK's delegation tool answers it, `Error running sub-agent: <reason>` with `status="error"`, and reported at once through the turn's live events as one recoverable `ERROR`, `<agent> failed: <reason>`, the sub-agent's run's: the coordinator carries on. A sub-agent's overflow (still too long after its summary) is warned of in the words of ADK's overflow handler, `<agent>: the request no longer fits <model>'s context window.` with `error_code` `CONTEXT_OVERFLOW` (`context.py::subagent_overflow_message`, both backends); what differs: ADK answers the sub-agent's model call with text ("I could not do this task: …"), so its run completes, while on Deep Agents the parent reads the error and the run fails. A refusal is no exception here (the framework adds no `ModelRefusalMiddleware`): a sub-agent whose final answer a model refused ends its run `refused`, and its parent reads Deep Agents 0.7.34's notice ("The subagent stopped because a model refused the request. … Retrying the same request is unlikely to succeed; rephrase it or continue without it."), on both backends and whichever deepagents the pin installs (0.7.28 has no notice of its own; 0.7.34+ finds no refusal block left to word again); an answer cut at the output limit keeps its text, followed by `[cut off at the output limit]`, and its run ends `completed` and `partial`, with one recoverable warning ("<instance>'s answer was cut off at the output limit"); the answer's thoughts or reasoning are kept. ADK's `SubAgentOutcomePlugin` and Deep Agents' `SubAgentOutcomeMiddleware` rewrite and mark the answer, by `workflow/agents/outcome.py`. On ADK the plugin reads the answer's `finish_reason` (Claude's `refusal` and a Chat Completions `content_filter` arrive as `SAFETY`, `max_tokens` and `length` as `MAX_TOKENS`, Gemini's as themselves), the `error_code` ADK sets on an answer with no content (a Gemini prompt's `block_reason`), the `reason` an `OTHER` stop names in its JSON error message (ADK's OpenAI Responses adapter's `incomplete_details`, `content_filter` among them) and a text part `OpenAI refusal: <text>` (that adapter's refusal, and `OpenAICompatibleLlm`'s of a Chat Completions `refusal`, which ADK's class drops). On Deep Agents the middleware reads `response_metadata`'s `stop_reason` (ChatAnthropic), `finish_reason` (ChatOpenAI, ChatGoogleGenerativeAI), `incomplete_details.reason` (the Responses API) and `prompt_feedback.block_reason` (a Gemini prompt block), and a refusal the answer holds (a refusal block, standard or `non_standard`, or `additional_kwargs["refusal"]`). The root's own answers reach the user as their model gave them: on ADK a root's refusal with no answer (Claude's, Gemini's) is still the turn's one `ERROR` ("<model> returned no answer"), and a root on OpenRouter or an OpenAI-compatible server replies "OpenAI refusal: <text>". On ADK a sub-agent's model failure is answered the same way: ADK's `_SingleTurnAgentTool` hands its parent "Error running sub-agent: …" (its reason ADK's wrapper's, "Dynamic node <agent> failed"), and `ADKEventProcessor` turns the sub-agent's error event into the recoverable `ERROR` (config-built apps). On both backends the root's own failure leaves the run: the turn's one `ERROR`, which Deep Agents' processor attributes to the innermost failure no `task` call answered. A gate or error result goes back as the call's `ToolMessage` with `status="error"`. LangGraph's `ToolNode` runs with `handle_tool_errors=True`.
- **Tool result cap**: every tool result passes `workflow/tool_output.py::cap_tool_result` (registered, MCP and skill tools, `job_result`, a sub-agent's answer on either backend): one over `tool_result_max_chars` is cut to its shape and as much of its head and tail as fits (the kept length is bisected, since JSON escapes vary), with a note (under `truncated`, or appended to a string) pointing at its full output in `./.{app_name}/tool-output/`, written for `read_file` to page by lines (lines over 2,000 characters split). On ADK, `workflow/adk/tool_result_cap_plugin.py::ToolResultCapPlugin` is registered after `InterruptedCallsPlugin`, since ADK stops at the first `after_tool_callback` that returns a value, and it leaves out an agent with `after_tool_callback`s of its own (a native YAML app's, `build.own_after_tool_agents`), which ADK would skip once the cap answered. ADK's Claude and OpenAI Responses adapters send only a result's `content`, else its `result`, so the plugin also puts the note there (`_note_where_sent`). On Deep Agents, `ToolResultCapMiddleware` sits between the permission gate and `ToolCallErrorMiddleware`, so an error result is capped too, and reads a `ToolMessage` (a JSON object cut as a dict, other text as a string, text blocks joined into the first) and each `ToolMessage` of a `Command`. A call of the framework's `read_file` (by identity, as each gate resolves tools) on a saved output is cut without a second save. Saving never fails the call (`tool_output_not_saved` warns once per folder, then debug), and a cap that raises leaves the result uncut (`tool_result_cap_failed` at warning, its traceback at debug).
- **Summarizing on ADK (main agent only)**: every app's App (a native ADK YAML app's too, when its root's model has a context budget) has ADK's `EventsCompactionConfig` with `workflow/adk/compaction.py::AgentCliSummarizer` at the root's trigger (`context_budget`, as on Deep Agents); ADK checks before every agent's model call, and `MainAgentPlugin` (the first plugin) records the running agent in a ContextVar, so the summarizer writes only for the root: a sub-agent compacting the shared session lost its brief and looped (100 requests in one turn, offline). The summarizer picks its own range before paying for anything (`summary_range`: the newest `keep` tokens and the current turn kept, a cut only where a user turn starts, never parting a call from its result, long-running calls excepted since ADK re-injects them, nor leaving a kept event stamped inside the range; none for a saving under 20% of the trigger, the seed left out of it), writes on the root's own model (`_simple_model(SUMMARY_MAX_TOKENS, agent=root)`, thinking off) with `workflow/summary_prompt.py`, the rendering sized to that model's window (the middle cut, `MIDDLE_OMITTED`, the seed kept whole), and returns **user-role** text starting `SUMMARY_PREFIX` (a model-role first message is one Claude refuses), which the fit guard folds, after the memory index when the request has one, into the next user text (`fold_summary`), so no request holds two user messages in a row. `last_kept_turns` and `last_error` are for its callers: a manual summarizer warns of nothing itself. It reports through the turn's live events (`_run_and_stream` iterates the runner through `live_events.merged` under `reporting(live)`); any failure is one recoverable `ERROR` a turn, never raised to ADK. `NoAfterTurnCompactionRunner` overrides ADK's private `Runner._run_post_invocation_compaction` (contract-tested), so the prompt never waits for a summary after the answer. `FitGuardPlugin` is the last plugin (but `SentRequestLoggingPlugin`, which logs a request as sent, and `CallSentPlugin`, which starts the call's clock) and `OverflowPlugin` the one before it (`MemoryIndexPlugin`, when the root has a memory tool and `memory_index_enabled` is on, the one before that: it puts the conversation's memory index snapshot first in the root's requests, never in the session): the guard leaves a request's oldest turns out when it is over its agent's budget (keeping the newest turn and what opens the conversation, the memory index then a summary: `protected_head`) and keeps each request as it came in (`request_as_seen`: one copy per model call, under the call's `EventActions`, which ADK passes to all three of its callbacks, since two parallel delegations to one sub-agent share the invocation and the agent name; each run drops what a cancelled call left), and the overflow handler, on a provider's overflow, summarizes now (the root, through `compact_session`, ADK's private `_run_compaction_for_token_threshold_config`; `_summarize_now` returns `WrittenSummary(text, kept_turns)`, and the retry is the index, the summary and those turns) or trims to half the budget (a sub-agent, or nothing to summarize), builds the retry from the guard's copy without the context cache, retries once on the agent's `canonical_model`, then answers the root with `LlmResponse(error_code="CONTEXT_OVERFLOW")`, never model text (ADK would store it as the reply), which `ADKEventProcessor` maps to the turn's `ERROR`; a retry that fails otherwise propagates, and `_run_and_stream` unwraps ADK's plugin-manager `RuntimeError` to the provider's error; a sub-agent answers with text ("I could not do this task: …") and one live recoverable `ERROR`, with no `error_code` on its response (that would be a second warning). A native ADK YAML app gets all of it: only the building of its agents differs (`workflow/adk/build.py`). Its chat-mode sub-agents keep transferring, and an agent the root transfers to replies to the user (`build.reply_agents`: its text is the reply, recent_messages reads it, its overflow is the turn's clear error, its calls write the outside-content mark); the summary and the memory index stay the root's, so such an agent is trimmed by the fit guard, not summarized. An agent's own callbacks (a native app's) run after every plugin, and only when none answered: its before-model callbacks see the request after the fit guard, and the cap leaves out an agent with after-tool callbacks. A main agent whose model does not resolve through the catalog has no budget and no summary.
- **Sub-agents delegate and return**: on both backends a sub-agent is a tool call of its parent's that returns its last text in the same turn; only the root replies to the user (a sub-agent's `TEXT` carries `metadata["subagent"]`, and the CLI shows it as the events box's status line, under its run's name: `researcher-2 › …`; `/agents` lists a conversation's runs), and the next turn starts at the root; fact extraction reads only the user's and the root's text, and a sub-agent without a description is offered as "The <name> agent." with a warning. `AgentConfig.inherit_context` sets what it sees: False (the default) the request alone, True its parent's conversation too; `validate_agent_graph` refuses a value that is not True or False, `inherit_context=True` on the root and, in 0.7.0, on an agent with sub-agents (Deep Agents tells a fork that delegating "will be refused") or below another sub-agent. On ADK (`workflow/adk/delegation.py`) every config-built agent but the root is `single_turn` with both `disallow_transfer_*` set, so ADK offers none of them `transfer_to_agent`, and an inheriting one passes `include_contents="default"` explicitly (ADK forces `"none"` on a `single_turn` agent unless the field was set) and ends the agent's instruction with `INHERITED_CONTEXT_NOTE` (whose conversation it reads, which message is its task: ADK sends it the user's turns as plain user messages); a sub-agent named like one of its parent's tools fails the build. On Deep Agents a fresh sub-agent is isolated and an inheriting one a fork (`mode="fork"`; its `LangChainBetaWarning` filtered to a debug log, `deepagents_fork_beta`), and `ForeignReasoningMiddleware(kind, agent=...)` leaves out the reasoning of AI messages another agent wrote. A native ADK YAML app keeps transferring (chat-mode sub-agents); a task-mode agent in one is refused at validation, since ADK runs its delegation outside the tool pipeline and keeps the call open across turns.
- **Token usage**: every model call the framework makes is one `LLM_USAGE`, on both backends, side calls included (`generate_simple`: `summarize`'s, `purpose` `tool`; `on_session_end`'s, `memory_extraction`, outside any turn; an app's own, `side_call`, or what its caller names with `workflow/usage.py::side_call`), its counts normalized where it is made (`normalized_tokens`: `prompt_tokens` every input token, cache reads and writes included; `completion_tokens` every output token, thinking included; ADK's read by its model's provider kind, `adk_usage_event`/`adk_tokens`, since Gemini and ADK's Claude adapter keep the thinking apart from the candidates and OpenAI's count it inside, an agent of no known kind read as apart; Deep Agents' by LangChain's one convention, `langchain_tokens`; the raw log's usage records alike), and timed (`latency_ms`: on ADK from the request to the answer, `workflow/adk/call_clock.py`'s plugins marking the answer's `custom_metadata`; on Deep Agents by the turn's `RunCallback`, which marks the answer's `response_metadata["agentic_cli"]`, beside the outcome mark; a side call, a summary and the overflow retry around their own request; no adapter sends either mark). Each is recorded in its conversation's ledger (`UsageLedger`; `BaseWorkflowManager.usage`/`usage_of`, in memory for the manager's life: a backend switch's new manager starts afresh, as with `agent_runs`) where it is made, before `on_event` (the event processors, ADK's summarizer, as soon as its call answers, Deep Agents' `RunCallback`, `_report_side_call`), under the run it is made in and its conversation's turn while one runs (as the manager counts them, `/compact` and job notices included: not `SessionInfo.turns`; none in another conversation's turn or from a task its turn outlived, which `_report_side_call` reports to no one); a sub-agent run's `AGENT_RUN` end carries what it used, by model (`metadata["usage"]`, `RunRecord.usage`). The CLI's status bar sums the events it sees (the open conversation's total, on any backend); `/status` shows the ledger by agent. LangGraph (deprecated) records no ledger.
- **Tool registration**: Use `@register_tool(category=..., capabilities=..., description=...)` decorator. `capabilities=` is required — pass `EXEMPT` for tools that need no permission check or a list of `Capability(name, target_arg=...)` tuples the engine matches against rules. Tools are auto-discovered via the global `ToolRegistry`. A tool in `AgentConfig.tools` that the registry did not issue is denied at every call; building the agents names it once (`tool_not_registered`, per agent and tool: `BaseWorkflowManager._name_unregistered`): a plain callable, a `FunctionTool`/`StructuredTool` judged by the function it runs (as the gates unwrap it), an app's own tool class; ADK's own tool objects excepted (a built-in runs inside the model). `outside_content=True` (or a function of the call's arguments) declares that a call brings content from outside the user and the project into the conversation (a page, a document, a program's output): once the gate allows one, a memory write in that conversation is approved per call (see Permissions); an application's tools are unmarked unless they declare it, and a variant must declare the same flag as its tool.
- **Async tools never block the event loop**: a synchronous tool runs on a worker thread on both backends; an async tool runs on the event loop itself, where a blocking call (DNS, a connect, a file lock's wait, a sleep, a subprocess wait, PDF parsing, page conversion, embedding) freezes the whole app, Ctrl+C included. An async tool runs its slow work with `asyncio.to_thread`. `tests/tools/test_async_tools_never_block.py` lists every async tool (the registry's, the factories' service-bound variants, Deep Agents' skill tools), so a new one fails until it is listed, and calls each through the loop guard (`tests/loop_guard.py`).
- **Permissions**: `workflow/permissions/` holds a framework-independent engine that evaluates declared capabilities against rules from: builtin; `settings.permissions` (trusted, allow and deny: the union of the app's class default, the user file, the environment and the constructor, built at load; `store.settings_rules`, so the engine never reads the user file itself); the project file's deny rules (`store.load_project_denies`: its allow rules are ignored, each entry is checked with `PermissionRuleConfig`, a malformed one skipped with `permission_project_rule_invalid`, a file that is not a JSON object with `permission_project_file_invalid`, nothing raised; started from home it is the user file and is not read again); the saved grants; the in-memory session. The builtin rules allow reading the project, the KB and memory, and deny what the OS sandbox protects, both built from `agentic_cli/protected_paths.py`: reading or writing the credential stores; reading the app's keys and settings (`~/.{app_name}/.env`, `~/.{app_name}/settings.json`, and every env file the settings read: `store.settings_env_file_denies`, a relative entry anchored at the workdir) and the project's env files at any depth (`${workdir}/**/.env`, `.env.*`, `.envrc`: engine only, the sandbox hides the root `.env`); writing `~/.{app_name}` (settings, grants, jobs, sessions), shell start-up files (zsh's, bash's, fish's), `~/.gitconfig` and `~/.config/git`, `~/.claude`, system directories, the project's `.git` and `./.{app_name}`. The sandbox hides all of `~/.{app_name}` from executed code, but the engine denies reading only its keys and settings: an app may keep files there for its agent (a `workspace_dir`, the sandbox's artifacts). Deny wins, so no user rule or grant reaches them. The `${workdir}/**` read allow (`store.WORKDIR_READ_ALLOW`) is left out when the workdir is one a grant may not widen to (`/`, home, above home): started there it would cover all of home, so reads ask; two builtin allows keep `./.{app_name}/tool-output/**` and `./.{app_name}/fetched/**` readable wherever the app starts. Interactive "Allow always" grants persist to `~/.{app_name}/project_grants.json` keyed by resolved project path — user-owned, never into the project settings file a repo could ship. ADK, Deep Agents and LangGraph gate tool calls via `workflow/adk/permission_plugin.py::PermissionPlugin`, `workflow/deepagents/middleware.py::PermissionMiddleware` (in every agent's stack, so sub-agents are gated as strictly as the root) and `workflow/langgraph/permission_wrap.py::wrap_tool_for_permission`. `web_fetch` saves every page it reads into `./.{app_name}/fetched/` (`tools/webfetch/saved.py`) as framework state, without a filesystem capability check: the location is fixed (the model never chooses it), a symlinked folder is refused, and cleanup only ever touches its own file names — so the builtin write deny on `.{app_name}/**` is about tools reaching into that path, not about this. The tool result cap saves full outputs into `./.{app_name}/tool-output/` (`workflow/tool_output.py`) on the same terms, and reading one back is an ordinary `read_file` the builtin allow for those two folders covers (`./.{app_name}` is denied only for writes; started from home it is `~/.{app_name}`, and only its `.env` and `settings.json` are denied for reads). `grep` searches no hidden file or directory below its `path` (the Python search filters them, also judging where a symlink leads; ripgrep gets a final `--glob '!.*'`, since a `file_pattern` glob overrides its own filter, and follows no symlink): the engine judges only `path`, and the project is readable. A `per_call=` hook (`BaseWorkflowManager._per_call_capabilities`: `memory.write` while the turn's conversation is marked, `workflow/outside_content.py`) skips the builtin allow and the grants for those capabilities (`Unstorable.OUTSIDE_CONTENT`: Allow once / Deny, the arguments shown), while a `USER` allow and any deny still apply; both gates mark the conversation when they allow a call that brings outside content (`brings_outside_content`; ADK's MCP tools by kind), in the manager's `OutsideContentMarks` and in the conversation's own state (ADK: the session-state key `agentic_cli.outside_content`, a conversation with events but no record counts as marked, from before 0.7.0; Deep Agents: `AgentCliState.outside_content`, first write wins; LangGraph: every conversation counts as marked), so a resumed conversation keeps it; a job's notice turn marks it too. `store.memory_folder_denies` denies writing `<workspace_dir>/memory` and `<workspace_dir>/projects` to the file tools; `exec_policy._protect_memory_folders` makes the folders (0700) before `execute_python`'s sandbox policy is built and denies them to the code (read and write, as subpaths: every project's scope), and on seatbelt also renaming the workspace and each ancestor the code may write (`deny_rename_paths`; bubblewrap's bind mounts follow a renamed ancestor), so the code cannot plant a memory even where `workspace_dir` is writable. ADK's `PermissionPlugin.before_model_callback` marks the conversation for what the model runs itself (a request tool that is more than function declarations: `google_search`, `url_context`, `retrieval`, `code_execution`, …; an agent's `code_executor`), which never reaches the tool callback.
- **Permission targets vs. patterns**: a tool argument is a *target*, a rule's target is a *pattern*. Matchers canonicalize them with different methods: `canonicalize_pattern` expands `${workdir}`/`${home}`/`${app_name}` and anchors relative filesystem patterns to the project; `canonicalize_target` expands nothing and resolves a path exactly as the tool will. Any tool that takes a path argument must resolve it with `agentic_cli.paths.resolve_path` (the same function `PathMatcher.canonicalize_target` uses), so the engine judges the location the tool acts on. A URL, pattern or target, is `agentic_cli.urls.canonical_url` of it (`URLMatcher`; a pattern keeps its `*`/`**`): the URL httpx sends, so `/x/../admin`, `/%61dmin`, `host.` and `host。com` are the page and host they reach; one httpx cannot send raises `ValueError` (a target is denied, a rule or saved grant skipped with `permission_rule_skipped`). `web_fetch`'s blocked domains compare the same host (`URLValidator`, `canonical_host` for each entry), and `PinnedTransport` resolves and sets the TLS name from `request.url.raw_host`, the host the Host header names. `tests/tools/test_path_contract.py` fails when a new filesystem tool has no contract case. Filesystem, `http.*` and shell capabilities must name their resource (`target_arg=` or a fixed `target=`): registering a tool with a targetless one raises `ValueError` (it would resolve to the wildcard, which is never remembered as a grant), and saved `http.read *`-style grants are dropped on load. Filesystem grants cover the named directory (a file's own directory), never `/`, home itself or anything above it (compared caseless): a file directly in home is granted exactly. The prompt names each exact target, then, when a session or "always" grant would cover more, `(for this session / always: all of <scope>)`; a sub-agent run's prompt opens with that run (`researcher-2 (researcher, run 1) wants to use …`: the engine builds it with `get_active_run()`, which both gates run inside, and the request carries it, `UserInputRequest.run`), and its grants are shared by every agent; an `http.read` grant covers the URL's site (`engine.site_scope`: `https://host/**`, the exact canonical host, HTTPS, no IP literals or local names). A deny rule is matched with the matcher's `matches_deny`: a `filesystem.*` deny ignores case and Unicode normalization (`PathMatcher.matches_deny`, NFC then casefold: on APFS `./.ENV` is `./.env`), the other matchers deny as they allow; an allow compares case, so another spelling of an allowed path asks. A grant is a literal target matched as a pattern, so it is remembered only when the literal part of its rule (the scope directory or exact path, `*` `?`; an exact URL, as `engine._is_literal_url`; a site scope is literal; any other target whole, `*` `?` `[`) holds no wildcard character (`engine.is_storable_grant`); otherwise the prompt offers "Allow once" and "Deny" and says why, and a saved allow whose literal part holds one is dropped on load (`permission_glob_grant_dropped`, `engine.is_literal_saved_grant`), as is a saved filesystem grant on `/`, home or above it (`permission_broad_grant_dropped`, `engine.is_bounded_saved_grant`).
- **Service registry**: Tools access services and shared state via `get_service(key)` from `workflow.service_registry`. A single ContextVar holds a `dict[str, Any]` set by the workflow manager during processing. Complex services (KnowledgeBase, SandboxManager, MemoryStore) are lazily created; simple state (plan string, task list) lives directly in the registry dict.
- **Manager detection**: tools declare their own service needs — `@register_tool(..., requires="knowledge_base")` (or a tuple for several) — and the key is validated against `service_registry.KNOWN_SERVICE_KEYS` at registration (only *constructible* services are declarable). `BaseWorkflowManager._detect_required_managers()` reads that metadata off the registry for each agent's tools (by registry identity, so `register(func, name=...)`'s original callable still declares its services); `_build_services()` then lazily constructs only the services actually needed, into a local dict that is released in full if a later constructor raises (nothing is published, so nothing else could close it). Each framework service is one row of `workflow/services.py::SERVICES` (`ServiceSpec`: how it is built, how it is closed, the tools it gives, whether a tool may declare it, how its references to its owner move), and `KNOWN_SERVICE_KEYS` and the closers are read from that table. A downstream tool may request any framework-provided service without editing the framework; there is no mechanism for registering new service *types* (a backend that builds one of its own overrides `_build_services_into`, `_get_service_tool_map` and `_SYNC_SERVICE_CLOSERS`).
- **Canonical tool names + permission identity**: `ToolDefinition.name` is the single identity. `register_tool(name="public_name")` wraps the callable so `func.__name__` is the registered name (backends derive the model-visible name from the callable). Permission gating **and tool assembly** resolve through a **registry-owned identity binding**: each `ToolRegistry` owns a `id(obj) → (weakref, definition)` map (`registry.bind_identity()`/`identify()`; the module-level `tools.registry.bind_tool_identity()`/`identify_tool()` answer for `get_registry()`). Every hit is confirmed with `is` against the weak reference, so neither a name, a class name, nor a forged `__eq__`/`__hash__` can stand in for it, and a recycled address inherits nothing. Identity is **per registry** — a tool registered into an application's own `ToolRegistry` is not one of the framework's, so it stays untouched during assembly and is denied at permission time — which is also what lets a short-lived registry, its definitions and their closures be garbage collected. Everything the framework issues is bound at its construction site: registered callables, factory service-bound variants, renamed wrappers, and the native ADK tool objects the framework builds (skill tools, in `tools/skills/toolset.py`; each sub-agent's delegation tool, in `workflow/adk/delegation.py`). ADK appends its private `_SingleTurnAgentTool` (named after the sub-agent, no `.func`) to a parent's tools in the parent's constructor, so `_build_agent` binds them right after `LlmAgent(...)` returns, to the exempt `task` declaration (`tools/_core/delegation.py`): only `type(t) is _SingleTurnAgentTool and t.agent is` a child the framework built and passed in. An application's `AgentTool`, a subclass, a same-named look-alike, a second `_SingleTurnAgentTool` around the framework's own child, or one around an agent the framework did not build stays unbound and is denied; `tests/workflow/test_adk_delegation.py` pins each, and contract tests pin the private class and its `agent` attribute. `workflow/adk/permission_plugin.py` unwraps `.func` only for the exact ADK types whose contract is to call it (`FunctionTool`, `LongRunningFunctionTool`, and ADK's own `TransferToAgentTool`), and gates genuine `McpTool` instances (`isinstance`, since ADK creates them on connect) under a synthetic `mcp` capability. `TransferToAgentTool` is a `FunctionTool` **subclass** ADK auto-injects into an agent that can transfer (a native ADK YAML app's: config-built agents delegate instead); matching only exact `FunctionTool` denied the built-in routing tool as unregistered, so delegation could not work at all. It is trusted on exactly the same terms as the others — ADK constructs it as `super().__init__(func=transfer_to_agent)` and overrides only `_get_declaration()` (to add the agent-name enum), never `run_async`, so what it invokes is still exactly `self.func`. Listing the **exact class** keeps every other subclass, forged object and same-named tool denied; no name authority is restored. Deep Agents' `PermissionMiddleware` follows the same rules: bound objects first, then `.coroutine`/`.func` of an **exact** `StructuredTool` only (`workflow/deepagents/tools.py::to_langchain_tools` builds one whose `.func`/`.coroutine` *is* the registered callable, and hides a `tool_context` parameter, passing `None`, so an ADK-style tool loads unchanged). The objects it builds or receives are bound where they are made: the `task` tool `SubAgentMiddleware` creates, to the `task` declaration (`tools/_core/delegation.py`), right after the middleware is built; the LangChain skill tools (`tools/skills/langchain_tools.py`), to the definitions `tools/skills/permissions.py` registers for ADK's, so ADK and Deep Agents gate them alike; and each MCP tool, in the manager's own map (`mcp_tools.MCPSessions.identify`, consulted before the registry, never the registry itself), to a synthetic definition under the `mcp` capability with the tool's (prefixed) name as the target. Anything unbound is denied — and, in assembly (service detection, service-tool substitution, canonicalization, long-running wrapping), left exactly as the application supplied it: a plain callable named `kb_search` is not the framework's tool and must not be given its services, its service-bound variant, or its long-running contract. Substitution additionally requires the service variant to *be* that same definition (`identify_tool(variant) is definition`); factories bind each closure to the exact module-level tool it re-binds, so a tool an application has taken over keeps its own implementation.
- **One name, one tool**: `ToolRegistry.register()` raises on any name that is already registered — matching capabilities are *not* grounds for sharing one, since they say nothing about the docstring or the model-visible schema. Sharing is declared, never inferred: `declare_tool(name, ...)` (exported from `agentic_cli.tools`) declares a tool that has **no backend-neutral implementation** (`ToolDefinition.func is None`), and each backend registers its own with `register_tool(..., variant_of=name)` — same identity and permission contract, its own signature and docstring. Re-declaring the same contract is idempotent; changing its description or capabilities raises. `definition.variants` is ordered by defining module, so it never depends on import order, and assembly substitutes a variant's canonical callable via `registry.canonical_for()` (never `None`). A `replace=True` retires the previous definition's callables, and retired backend variants are excluded from `include_state_tools` injection, so the model never sees two tools with one name. That is how the ADK and LangGraph `save_plan`/`get_plan`/`save_tasks`/`get_tasks` coexist (declared in `tools/_core/state_tools.py`); previously they contested the name and import order decided the winner. Deep Agents' delegation tool `task` is declared the same way (`tools/_core/delegation.py`, at `agentic_cli.tools` import, before any application tool registers), so an application's `register_tool(name="task")` raises on every backend, and a Deep Agents coordinator whose own tools include one named `task`, or an agent with skills whose own tools use a skill tool's name, fails to build with `AgentGraphError`. A bare-name reference to a declared-only tool raises "ambiguous" rather than guessing a backend. `replace=True` takes a name over deliberately and **retires the old definition's identities**, so its callables resolve to nothing (denied, and left alone by assembly) rather than inheriting the replacement's capabilities.
- **Turn/lifecycle concurrency**: a manager runs one turn at a time — `process()`/`resume_with_job_result()`, and `compact()` (`/compact`), enter through `_turn()` (the base's: the conversation named in the log context, then `_turn_admission()`, which holds `_turn_lock`, then `_workflow_context()`; job resume, `can_resume` and `compact` are the base's templates over the backend's hooks), and `reinitialize`/`cleanup` (the base's, for ADK and Deep Agents: a backend implements only the release's hooks) hold `_lifecycle_lock` **and** `_turn_lock` (`initialize_services` only `_lifecycle_lock`). Lock order is lifecycle → turn; a turn initializes *before* taking the turn lock, which is what keeps the two from deadlocking — and because of that a cleanup can land in between, so admission re-checks `_backend_ready()` while holding the turn lock and reinitializes once (or fails cleanly) rather than running against released resources. Initialization is transactional: services are built on a worker thread into a *local* dict and published only while the attempt still owns init (a cancelled attempt releases what the thread went on to build), and a failed attempt rolls back. A failed in-place reinitialization leaves the manager uninitialized; the controller reports `FAILED` and refuses to hand it out, but **keeps** it so a retry can revive it with its preserved (possibly in-memory) sessions intact. `WorkflowController` serializes init/reinitialize/swap/close on its own lifecycle lock, and a background init that finishes after `close()` releases its manager instead of publishing it.
- **HITL callback is context-local**: `set_input_callback()` stores into a per-manager `ContextVar`, so a second consumer installing its callback cannot capture a running turn's prompt, and one consumer's `clear_input_callback()` cannot unregister another's. `MessageProcessor` cancels and awaits its consumer task **before** clearing the callback, so no tool is left asking a question nobody owns. And the callback answers only inside its turn: a task a turn started (`asyncio.create_task` copies the context, the callback with it) that asks after the turn ended gets `UserInputUnavailable` (`request_user_input`; the turn's span, `workflow/sessions.py::open_turn_scope`/`close_turn_scope`, opened and closed by `_workflow_context`, which the copy carries), as with no approver: a question goes unanswered and a permission ASK is denied by the engine's no-approver rule.
- **Code that may run on the host is approved per call**: CPython has no in-process sandbox, so `execute_python` runs inside the OS sandbox or not at all by default (`os_sandbox_strict` true: no backend, a failed wrap, or a sandbox tool that fails as it starts (the runner's first stderr line, `_STARTED_MARKER`, never came) is a refusal that keeps its cause and ends with `executor.how_to_run`: sandbox-exec, bwrap and Ubuntu 24.04's user namespaces, none on Windows, and the opt-out where it lives, `exec_policy.sandbox_opt_out`: `~/.{app_name}/settings.json` or the env variable, since the project file and `/settings` cannot set it), and the module set is chosen from the path a call takes (`executor.py::_choose_run`, then `validate_code(allowed_modules=)`). The engine never imports `tools/`: `BaseWorkflowManager` passes `PermissionEngine(uncontained=tools.exec_policy.uncontained_exec_capabilities)`, called with the settings at each check (a settings change applies at once). For a capability it names, `engine.unstorable_reason` is `UNCONTAINED` (the one decision, shared with the prompt: only "Allow once" and "Deny", with its note), and `_evaluate` skips allow rules from grants (`SESSION`, and `PROJECT`, the user's `project_grants.json`), so a grant from when the code ran contained approves nothing; a `USER` rule still applies. A prompt for `*.exec` shows all of the code (the dialog body scrolls).
- **No harness-level turn replay**: ADK persists a turn's input during invocation setup, and Deep Agents' checkpointer at the turn's first step, so the CLI never re-invokes an event source. Retries belong to the provider client (`HttpRetryOptions`). `MessageProcessor` returns a typed `TurnResult`. A turn that fails yields one `ERROR` and returns, on both backends (the base `process()`'s contract; `WorkflowEvent.turn_failed`: the error's text, `rate_limited`, `error_type`); an `ERROR` the turn already yielded that is not recoverable is its one; a cancel still raises, and a turn that cannot start (initialization, admission, or its conversation cannot be read) raises before any event. The CLI says a rate limit from the event as it does from a manager that raises.
- **Interrupted calls**: Ctrl+C stops the whole turn (loop, model calls, tools, sub-agents), and every call the model made gets exactly one result (`workflow/interrupts.py`, the texts and `OpenCalls`, each manager's record, kept by conversation and by the run that made each call (the root's own, or a sub-agent's: a provider that numbers its call ids per agent gives a sub-agent's call its parent's delegation's id): a call's result as it finished, a call `asking` at its permission prompt, both gates marking it; a conversation whose turn the user cancelled): a finished call keeps its result, a running one or a delegation is `INTERRUPTED_BY_USER`, one at its prompt `NOT_RUN`, one whose job was submitted the job's state (`job_started`); a cancel with no call open leaves `MARKER` as the main agent's reply; a call nothing answered (a crash, an old session) is `INTERRUPTED`. On ADK the turn runs with `abort_signal`, set by `live_events.merged(on_stop=)` before the runner is cancelled, so ADK seals the invocation in its own branches; `merged` waits for its source to close, a repeated cancel too (up to `STOP_GRACE`), and `process()`/`resume_with_job_result()` close their inner generators with `aclosing`, so a run never outlives its turn. `adk/interrupted_calls_plugin.py::InterruptedCallsPlugin` (before `ToolResultCapPlugin`, every app) sets the active tool call around each call (`before_tool_callback`, so a question marks it `asking`), records results with their `state_delta`/`artifact_delta` in `after_tool_callback` (not a long-running starter's `None`: its job answers it), keeps the cap's cut of one (`ToolResultCapPlugin.on_cut`, so a seal sends that cut and its full output is saved once) and rewrites the seals (`error_code` `INVOCATION_ABORTED`, contract-tested) in `on_event_callback`, carrying those deltas, each seal answered from the record of the run its branch names (a seal is written outside that run). ADK's seals pair a result with a call by id alone, so a call whose id a sub-agent's result used is left open: the manager answers those as the stopped turn ends, before it clears the record, the same way (`_answer_unsealed`, shielded; `unsealed`, once ADK's seals are written), so a call that finished beside a delegation keeps its result. `left_open` answers leftovers when `process()` starts (every app: a task-mode agent's delegation, which ADK keeps open on purpose, is refused at build, and ADK's client calls for a human, `adk_request_confirmation`/`_credential`/`_input`, are answered as interrupted, since the manager offers no way to answer them), a result pairing with a call on its own branch only; one a stop left because its answers could not be written is answered `INTERRUPTED_BY_USER` (the manager records the stop). On Deep Agents `InterruptedCallsMiddleware` takes `PatchToolCallsMiddleware`'s place, first in every stack: it records each final `ToolMessage` with the rest of its `Command` update (outermost tool wrapper) and answers open calls in `before_agent`, returning those updates too; the root adds `MARKER` before the new input when the message before it is no reply (a `HumanMessage` or a tool result). Background jobs are not part of the turn: they keep running. Nor is a synchronous tool's function (a sandbox cell, `compile_document`, `execute_python`): it runs in a worker thread on both backends (ADK's tool thread pool, LangChain's executor), which Python cannot stop, so its call is answered at once but the function runs on to its end, keeps its sandbox session busy (the session's next call waits for it) and holds the process's exit until it returns (the sandbox's cleanup stops a cell). So is a knowledge-base ingest's store step (`kb_ingest_text`, `kb_ingest_file`, `ingest_arxiv_paper`: `KnowledgeBase._store` runs `ingest_document` in `asyncio.to_thread`): a cancelled ingest is answered `INTERRUPTED_BY_USER` and still stores its document, so a model that retries it stores a second copy; a cancelled `sidecar` or `backfill_sidecars` keeps its lock or flag until its thread's call ends (`memory/kb/manager.py::_Threads`).
- **Session identity**: durable sessions are addressed by `SessionRef(app_name, user_id, session_id)` (`workflow/sessions.py`). Every session hook (`session_exists`/`list_sessions`/`session_info`/`delete_session`/`recent_messages`/`load_session`) takes an optional `user_id`, defaulting to `settings.default_user` only when the caller omits it. `list_sessions(limit=)` returns `SessionInfo` rows, newest first, and `session_info` one conversation's or None: the title is the first prompt (`session_title`), the turns what the user typed (a job's notice or resume, a delegated request and a summary are none), `updated` when it last changed. ADK keeps the title and the turns in two session-state keys saved with each user turn (`workflow/adk/sessions.py`, `run_async(state_delta=)`; a conversation from before them is read from its events and never written back, which would move it in the list), Deep Agents keeps them in a session index, a LangGraph store beside the checkpointer (`workflow/deepagents/sessions.py`: each row written as a turn starts, its input counted, then from the newest root checkpoint as it ends and after `/compact`, so a listing reads no checkpoint; a database from before the index scanned once per app and user), LangGraph knows only the id; ADK's `delete_session` looks the session up first, so an unknown id is False. Backends without a session store leave `supports_sessions` False, and the base hooks raise `NotImplementedError` rather than answering with a misleading `False`/`[]`. Deep Agents keys each conversation's checkpointer thread by the whole triple (`workflow/deepagents/sessions.py::thread_id`, `json.dumps([app_name, user_id, session_id])`) and stores it in each checkpoint's metadata, so the backfill's scan filters by app and user and keeps the root namespace; sub-agents are compiled with `checkpointer=False` and store none (an older version's sit under `tools:<task-id>`, and `delete_session` removes them with the thread and the row, returning False for an unknown id). A backend's conversations are read without its manager through its `SessionReader` (`workflow/session_readers.py::open_session_reader`: the backend's own session code over its store, opened from the settings), so the CLI lists, opens and deletes the conversations of every installed backend (`cli/stored_conversations.py`): each row names its backend (`SessionInfo.backend`), and a conversation another backend keeps opens there (no index joins the stores, and an id two backends keep is two conversations).
- **Active turn**: the in-flight `(user, session)` is a `ContextVar` (`workflow/sessions.py::get_active_turn`), set with a token by `_workflow_context()`, which every turn enters through `_turn()` — concurrent turns on one manager stay isolated and nesting restores the outer turn. The tool call in progress is another (`get_active_tool_call()`, a `ToolCallRef(call_id, name)`), set by Deep Agents' `ActiveToolCallMiddleware`, innermost in the tool stack (after the gate and the error middleware, so only a call the gate let through runs as one); on ADK, `InterruptedCallsPlugin.before_tool_callback` sets it around each call (ADK's stand-in for an unknown tool name excepted) and its `after_tool_callback` resets it. The sub-agent run in progress is a third (`get_active_run()`, a `RunRef`; None in the root's own calls), set on ADK by `MainAgentPlugin.before_agent_callback` from the agent's invocation branch, and the parent's set again by its `after_agent_callback` and `on_agent_error_callback` (ADK runs a delegated sub-agent inside its parent's call, whose after-tool callbacks are the parent's), and on Deep Agents by `ActiveToolCallMiddleware` around a `task` call to one of the agent's own sub-agents (the whole sub-agent runs inside it): a sub-agent's model calls, tool calls, permission checks and questions see it. `JobManager.submit(resume_on_complete=True)` takes `call_id` from the active tool call when the tool passed none, and `call_name` when that is None too; every `submit` records the sub-agent run in progress as the job's `started_by` (`instance_of(get_active_run())`).
- **Job notifications**: both backends tell a finished job through the base's `resume_with_job_result` (a template: the record names its conversation, a turn of it (`_turn`), the conversation there (`_conversation_exists`), the job's result read on a worker thread (`JobManager.result` takes the jobs directory's cross-process lock), the notice `job_notice`, told by the backend's `_deliver_job_notice`; `can_resume` makes the same checks without the turn), and the CLI resumes where `supports_job_resume` and `can_resume` say so. On ADK a finished job is told to the conversation (the root, or a native app's agent the root transferred it to) as one user-role text, `tools/jobs/resume.py::job_notice` (the Deep Agents notice below), whoever started it: its call already has a result (the root's "pending", or a sub-agent's job id), and a second result for the call itself made ADK's rearranger send the call, that result and nothing between, so the root answered without the turns since. A native ADK YAML app's job is told the same way (it used to answer its pending call as a `FunctionResponse`, and needed `record.call_id`); a call still open (a starter that returned nothing) is answered first (`_answer_left_open`). A sub-agent's long-running tools are not wrapped (`_build_agent` wraps the root's only): ADK pauses the whole invocation on a pending long-running call, inside a delegation too, so a sub-agent's starter returns the job id as an ordinary result. ADK's `recent_messages` leaves the notice out by its header, since ADK keeps no mark on a message. The CLI delivers only the jobs that wait for the current conversation, by one rule (`cli/waiting_jobs.py`) for the deliveries, the status bar's `↻N` and the line startup says: a finished job flagged `resume_on_complete` whose delivery is still `PENDING` (`JobRecord.awaiting_resume`: not one being delivered), that is this conversation's, or has none, or whose conversation is gone, `can_resume` saying so and no other installed backend's store keeping it (`waiting_jobs.opens_anywhere`, `BaseCLIApp._kept_elsewhere`) (those two told it is unavailable): another conversation's waits until it is opened, `/resume` (`resume_session`) telling them when `job_auto_resume` is on, startup only naming them (`_name_its_waiting_jobs`: outside the input handler Ctrl+C cannot stop a turn); the status bar's `↻N` counts them whatever the setting (`↻N: /jobs resume` when it is off; its `can_resume` answers kept 30 s, forgotten after `/sessions --delete`, a conversation `/new` drops on the memory store, or a new conversation on another backend). On Deep Agents a finished job's result cannot be the pending call's second result (the call already has its `pending` one, and Anthropic and OpenAI take one result per call), so `resume_with_job_result` runs a turn whose input is one `HumanMessage`: `tools/jobs/resume.py::JOB_NOTICE_HEADER`, the ask (`job_notice_ask`: for the root's own job `JOB_NOTICE_ASK`, tell the user what it means: without it a model may say nothing; for a sub-agent's, `JOB_NOTICE_ASK_FOR`, the same ask naming the sub-agent), then `job_result_payload(record, result)` as JSON, a line each (`job_notice`), marked `response_metadata={"agentic_cli": {"kind": "job_result", "job_id": ...}}` (`workflow/deepagents/sessions.py::job_notification`). No provider adapter sends that field; `recent_messages`, and so fact extraction, leaves the message out; the checkpoint keeps it for the model. The root agent receives every job, a sub-agent's too (its run ended when its `task` returned), and the notice names the sub-agent whose call started it (`JobRecord.started_by`, its instance, from the active run at submit; `job_notice_ask`: "A background job researcher-2 started has finished…", the root's own `JOB_NOTICE_ASK`). `can_resume` needs the record's session and user and the conversation's thread, not a call id.
- **Resource ownership**: one release, `BaseWorkflowManager._release_resources` (cleanup, reinitialize and a failed initialization's rollback run it): it resets the base's state (`_initialized`, budgets, index snapshots, the catalog detached), takes the backend's closers from `_detach_backend()` (ADK: the runner, which closes the agents' MCP toolsets; Deep Agents: the agents' MCP sessions, handed over to a fresh `MCPSessions`) and `_detach_store()` (ADK: the session service; Deep Agents: the checkpointer, the session index and their connections), detaches the services through `_cleanup_managers` (the release's services hook: a backend's override runs; outside a release, as in LangGraph's cleanup, it closes them in place) and starts closing them on a worker thread (their closers block: `docker rm -f`, a kernel shutdown, the jobs directory's lock; on the loop they froze the app), then runs the closers (backend, store, catalog, then the services' close waited for last under a shield of its own: a hanging service close holds none of the rest, and a shutdown's cancel cancels no close not yet started) in one task awaited under a shield, each isolated (`_aclose_owned` for a duck-typed `aclose()`/`close()`): a cancel stops only the wait. The hooks are synchronous: one that returns an awaitable is closed and fails the release with a `TypeError`, after the rest is released. An override of `_release_resources` reads `self._keeping_store` to know whether a switch keeps the store. `cleanup()` is idempotent; `WorkflowController.close()` is the single shutdown path (cancel init → shut executor → clean manager). `reinitialize(preserve_sessions=True)` (a model switch) runs inside `_keeping(True)` (`_carrying_services` is its other name): the store is not detached and the services are carried, since session grants, sandbox kernels, jobs, knowledge bases and the conversations belong to the conversation, not the model, so neither the release nor a failed attempt's rollback closes them (a retry continues the conversation); the backend's own resources (ADK's runner, Deep Agents' MCP sessions) close and reopen. `_release_resources(keep_session_service=/keep_checkpointer=)` keeps the store, with a `DeprecationWarning`, until 0.8.0. LangGraph keeps its own `cleanup`/`reinitialize`. A run's services can move to a manager of either backend: `loan = old.lend_services()` (the table's services `old` owns, but itself), `await new.initialize_services(services=loan)` (borrowed, published, only what is missing built; no release of `new` closes them, so a failed, cancelled or abandoned start leaves `old` owning and using them), `await old.give_services(loan)` (between turns: inside one of `old`'s it raises `RuntimeError`; under `old`'s lifecycle and turn locks and `new`'s lifecycle lock: `new` owns them, each row's `rebind` moves the permission engine's `workflow`/`per_call` and the knowledge base's summarizer to it, and `old`'s release drops them unclosed). A manager holding services it does not own runs no turn (`_turn_admission` raises `RuntimeError`): the engine's per-call check reads its owner's outside-content marks, so `new` runs none before the give and `old` none after it until its release. The CLI's `WorkflowController.switch_backend` (a conversation opened or started on another backend) hands the run's services over so: lend, start, give, publish at once, release the old one.
- **Memory package boundary**: `agentic_cli/memory/` (the knowledge base in `memory/kb/`, the memory store in `memory/store/`, shared embeddings and atomic writes in `memory/_core/`) imports nothing from the rest of agentic-cli, and `kb` and `store` never import each other. The rest of agentic-cli uses only `agentic_cli.memory` and `agentic_cli.memory.kb`; `workflow/memory_services.py` is the one place settings become package arguments. The workflow exposes one `KnowledgeBase` (`memory.kb.knowledge_base`, provisional) over the project and user scopes, and one `EmbeddingService` for both scopes (the memory store searches by keyword). `tests/memory/test_boundary.py` enforces all of it, and tests under `tests/memory/` import only the package. A knowledge base summarizes only with the `summarizer=` it was given; the workflow passes itself when `knowledge_base_summarize` is on. Importing the package loads no other agentic_cli module (`tests/memory/test_loads_alone.py`), because the package root `agentic_cli/__init__.py` loads its exports on first use (PEP 562 `__getattr__`): nothing may be imported there eagerly, since Python runs it before every `agentic_cli.*` import.
- **Atomic writes**: Use `atomic_write_json`/`atomic_write_text`/`atomic_write_bytes` from `file_utils.py` for file persistence. They create files private (0600), right for the framework's own state; a write to a file the user owns (`write_file`, `edit_file`) passes `preserve_mode=True`, which keeps an existing file's permission bits (where the platform has `os.fchmod`: not Windows' Python before 3.13, whose bits mean nothing; `file_utils._fchmod`) and gives a new file the process default.

### Console Output
All console output must go through `ThinkingPromptSession` methods. Never use `rich.Console` or `print()` directly.
Log lines (structlog's and the stdlib logging's, which `configure_logging` points at `logging.py::LOG_STREAM`) and Python warnings go to stderr, but while the prompt runs, when stderr is the terminal (not `2>file`), `cli/app.py::_log_lines_above_prompt` adds each line to the session (`add_rich`), so it prints above the prompt: at once on the loop's thread (in order with the session's output), handed to the loop from any other; a line logged while one is shown goes to stderr. Written to stderr it landed on the prompt line and broke the screen. What is noise for a user is still logged at debug, so `BaseCLIApp.run()` installs `workflow/adk/log_filters.py::install_log_filters` (once per process; an app built but never run, a library user's or the test suite's, installs none, and importing the module imports no ADK: the filters attach by logger name): ADK's experimental notices, `[EXPERIMENTAL] feature … is enabled` and `[EXPERIMENTAL] <Class>: …` (a class ADK marks experimental, such as the `GeminiContextCacheManager` a caching Gemini agent builds), are logged at debug (`adk_experimental_feature`), and every other warning goes to the previous `warnings.showwarning`, written to `LOG_STREAM`; a filter on ADK's runner logger (`google_adk.google.adk.runners`) logs its "has no context_cache_config" advice at debug too (`adk_uncached_agent_transfer`). ADK gives that advice only to an app whose agents can transfer (a native ADK YAML app with sub-agents: config-built agents delegate) and that has no context cache: the ADK manager sets one (`_context_cache_config`) whenever `prompt_caching_enabled` is on and an agent runs on Claude or Gemini (for a native ADK YAML app, the models ADK runs its agents on, as resolved through the catalog), so the filter is for apps with caching off or no caching model. A filter on ADK's context-cache logger (`google_adk.google.adk.models.gemini_context_cache_manager`) logs a Gemini cache it could not create or delete at debug (`adk_cache_create_failed`, `adk_cache_cleanup_failed`): the turn goes on uncached. Filters on four ADK loggers log failure tracebacks at debug: compaction (`google_adk.google.adk.apps.compaction`, "Event compaction failed", `adk_compaction_failed`), node (`google_adk.google.adk.workflow._node_runner`, "Node execution failed", `adk_node_failed`), runner (`google_adk.google.adk.runners`, exactly "Root node %s failed.", `adk_root_node_failed`; "was cancelled" records pass) and plugin manager (`google_adk.google.adk.plugins.plugin_manager`, "Error in plugin 'context_overflow'": `overflow_plugin.OVERFLOW_PLUGIN_FAILED`, read as a record comes, `adk_overflow_plugin_failed`): the summarizer warns the user itself, and a failed model call or retry reaches the user as an `ERROR` event or the turn's error. A filter on ADK's rearranger (`google_adk.google.adk.flows.llm_flows.tools._rearranger`, "Dropping function calls with no matching function response", `adk_dropped_open_calls`) logs its warning on a call without a result at debug: the next turn answers such a call. Any other ADK warning that lands over the UI is handled the same narrow way, never by silencing the whole `google_adk` logger tree. Deep Agents' "Offloading conversation history to backend failed" warning and log (its summarization has no archive here, and the checkpoint keeps every message) are filtered as narrowly, to one debug log (`deepagents_history_not_archived`), by `workflow/deepagents/summarization.py::install_history_filters`. The LangGraph manager's `DeprecationWarning` is blamed on its caller (`stacklevel=2`), so Python's default filters keep it off the terminal when the factory builds it; a CLI user is told through the session instead (`cli/settings_ui.py::_warn_if_langgraph`: at startup, and on a `/settings` switch to `langgraph`).

Available session methods:
- `session.add_response(text, markdown=True)` - Display text/markdown response
- `session.add_rich(renderable)` - Display Rich renderables (Panel, Table, etc.)
- `session.add_message(role, content)` - Add message to history
- `session.add_error(content)` - Display error message
- `session.add_warning(content)` - Display warning message
- `session.add_success(content)` - Display success message
- `session.clear()` - Clear the terminal screen

## Testing

- **Framework**: pytest with `asyncio_mode = "auto"`
- **MockContext**: From `tests/conftest.py` — provides isolated settings and temp dirs for all tests
- **Model listings**: `tests/conftest.py::_no_model_listings` keeps every manager's model catalog unloaded (no network, no `~/.<app>/model_cache.json`), so any well-formed model id is accepted; a test that wants listings calls `tests/conftest.py::patch_catalogs` (a transport such as `tests/models/fakes.py::ProviderAPI`, the cache file or none), which keeps the real `build_catalog` and so every argument it gives. OpenRouter is a configured provider: `tests/models/fakes.py::openrouter_spec()` and `providers(openrouter="k")` define it, and a settings-level test sets `model_providers` and a fake `OPENROUTER_API_KEY` in the environment
- **Provider fakes**: model requests never reach a provider. Every offline test runs with the dead base URLs (the root conftest's autouse `_dead_provider_urls`, `tests/network_guard.py::dead_base_urls`: each built-in provider SDK's host variable at a dead local port, with `NO_PROXY` for it, and the variables that would override it removed: ChatAnthropic's and ChatOpenAI's host and proxy, LangSmith's gateway, the Vertex AI switches; a test marked `llm` keeps the real environment), so a built-in provider's client that a test did not route fails at once, locally; a test that needs an SDK's own default host deletes the variable itself. No run uploads LangSmith traces: the root conftest's `pytest_configure` removes the tracing switches once (langsmith caches its environment reads), and the live tests' key file never sets them. `tests/workflow/adk/fakes.py::FakeAPI` serves an ADK-built model's client (`serve()`) and records the bodies it sends; a native ADK YAML app's bare `claude-*` model builds its client from the binding ADK's `anthropic_llm` module made at import, which patching `anthropic.AsyncAnthropic` misses: `route_anthropic` routes both bindings; `tests/workflow/langchain_fakes.py`'s `route*` helpers send a LangChain chat model's client to it, with the SSE replies a LangGraph or Deep Agents turn needs. A test-first run against the old code must fail offline too, so stub any client the old code would build
- **Session fakes**: a session fake is `tests/cli/dialog_fakes.py::autospec_session()` (`create_autospec(ThinkingPromptSession)`), so a call to a method thinking-prompt lacks fails; `edited_dialog(edits)` is a real `Dialog` whose fields hold the user's edits (patch the module's `Dialog`). The render tests' `RecordingSession` and `RecordingThinkingBox` (`tests/event_replay.py`) are checked against the real classes by `tests/test_session_fakes_contract.py`. Turns on a real console run `tests/cli/console_app.py` over a pty (`tests/cli/test_console_turns.py`)
- **Deep Agents fakes**: `tests/workflow/deepagents/fakes.py::ScriptedChat` answers each model call from a script and records the requests, so a test drives a whole agent tree offline; patch `agentic_cli.workflow.deepagents.manager.build_chat_model` with `ScriptedModels(agent=[...])`. - **MockEmbeddingService** (`agentic_cli.memory`): keyword-only knowledge bases without ML dependencies; `tests/memory/fake_embeddings.py::FakeEmbeddingService` stores deterministic vectors and searches by meaning, no `kb` extra needed
- **`kb` extra tests**: import sentence_transformers or trafilatura with `require_kb_module(name)` (`tests/memory/kb_extra.py`), not `pytest.importorskip`. - **CI jobs** (`.github/workflows/ci.yml`): the offline suite runs on every change; the four jobs that each test one part (the kb extra, the built wheel, the LaTeX engine, Docker) run on a pull request only when it touches that part, and all five run on every push to develop and main. `.github/scripts/ci-jobs.sh` decides from the pull request's own diff (`tests/test_ci_jobs.py`): each part's paths; `ci.yml`, the script, `pyproject.toml` and `environment.yml` for all four; a module added or removed under `src/`, a file there that is not Python, or `.gitignore` (hatchling leaves out what it matches), for the wheel; a changed line of `workflow/settings.py` that names the sandbox for Docker (`sandbox_image` is the tag the job pre-pulls, which a test keeps equal). - **Loop guard**: `with tests/loop_guard.py::no_blocking_calls():` fails the test when a known blocking primitive (DNS, synchronous connects, `flock` without `LOCK_NB`, `time.sleep`, subprocess waits, an unfinished `Future.result`, pypdf, page conversion, embedding) runs on a thread whose event loop is running, and lets a worker thread (`asyncio.to_thread`) through. It judges by thread, not by timing; put a fake (a `socket.getaddrinfo` stub) in place before the `with`, since the guard wraps what is bound when it starts
- **Integration tests**: `tests/integration/` covers ADK, Deep Agents and LangGraph pipeline tests

### Live LLM tests (real API calls)

Tests that hit real provider APIs use the existing framework — **don't invent new gating or key handling.**

- **Marker**: `@pytest.mark.llm`; modules set `pytestmark = [pytest.mark.llm, pytest.mark.skipif(<no key>, ...)]`.
- **Key loading is handled by the live-test framework** (`tests/integration/conftest.py`) — keys are not
  plain shell env vars, so go through pytest rather than re-deriving it.
- **Run**: `-m llm` (live; needs network — disable the Bash sandbox) or `-m 'not llm'` (offline).
  A bare `pytest` run makes real API calls when keys are available.
- **Example**: `tests/integration/test_adk_claude_live.py`.

### Live docker sandbox tests (real container runtime)

The `jupyter_docker` backend's isolation boundary is verified against a real daemon. The
`jupyter_local` backend has none to verify: its kernel runs on the host as the user, and neither
backend blocks imports or scans the code (the container is the boundary).

- **Marker**: `@pytest.mark.docker`; skipped unless docker/podman is available. The bulk of the
  backend is tested offline via the faked `ContainerRuntime` seam (incl. an end-to-end run of the
  real `driver.py` as a subprocess) — these live tests only cover what needs a real container.
- **Run**: `-m docker` (needs a container runtime) or `-m 'not llm and not docker'` (offline CI).
- **Fail-loud in CI**: set `SANDBOX_REQUIRE_DOCKER=1` so a missing/broken runtime FAILS instead of
  silently skipping (a skip reads as green). CI: `.github/workflows/ci.yml` (offline + docker jobs).
- **Example**: `tests/tools/test_sandbox_docker_live.py`.
